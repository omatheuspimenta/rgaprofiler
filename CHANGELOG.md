## v0.2.1dev - [2026-10-02]

### `Changed`

- **CI runs only the tests that don't need the license-gated software.** InterProScan's database and the DeepLoc2/SignalP6/DeepTMHMM weights live under the git-ignored `softwares/` and can't be distributed, so every test using them failed on GitHub's runners (8 of 22 on the `v0.1.0` release, failing 6 of the 7 shards on the pinned Nextflow version). The 14 tests that run without them (FASTA_QC, the six `*_MERGE` modules, DeepCoil2, Phobius, InterProScan's mock-database test and the resource-sizing probe) are now tagged `no_licensed_software`, and `nf-test.yml` runs only that tag. The other 8, including the full pipeline test, still run locally with `nf-test test --profile +docker` (see `docs/CONTRIBUTING.md`). Checked locally in a clean clone without `softwares/`: 14/14 pass on every shard with Nextflow 25.10.4 and 26.04.6.
- **CI tests `-profile docker` only.** On pull requests into `main` the nf-test matrix also ran `conda` and `singularity`, which can't work here: every module except FASTA_QC ships only a docker image, and `docker` is the one profile the pipeline supports (`docs/usage.md`).
- Formatting only, no content changes: prettier (table alignment, YAML quote style), trailing whitespace and missing final newlines in the pipeline's own files.

### `Fixed`

- **`nf-core linting` failed.**
  - The pre-commit job (`prek`) reformatted vendored upstream tool code under `docker/`. That code is baked into versioned images, so `docker/` is now excluded from the prettier, trailing-whitespace and end-of-file hooks (the large-file and merge-conflict checks still cover it).
  - `nf-core pipelines lint` failed its `nf_test_content` check on `tests/resources.nf.test`, a resource-sizing probe with no `outdir` or `versions.yml`, and on `tests/nextflow.config`, which has no `pipelines_testdata_base_path` because the test data is bundled under `tests/testdata/`. Both are now listed as exceptions in `.nf-core.yml`.
- **The pipeline version now matches its release tags.** The `v0.1.0` release still declared `1.0.0dev` in `nextflow.config` (`manifest.version`), `.nf-core.yml` and `ro-crate-metadata.json`, so its runs reported themselves as `1.0.0dev`, including in `pipeline_info/` and the `pipeline_version` field of `run_metadata.json`. All three now say `0.2.1dev`.

## v0.1.0 - [2026-10-02]

Initial release of omatheuspimenta/rgaprofiler, created with the [nf-core](https://nf-co.re/) template.

### `Added`

- `--num_blocks`: split each sample's input FASTA into a fixed number of sequence blocks (instead of a fixed sequences-per-chunk size via `--fasta_qc_chunk_size`), which DeepCoil2, InterProScan, DeepLoc2, SignalP6 and DeepTMHMM now all run once per chunk over (previously only InterProScan was chunked) — each with its own `*_MERGE` process reassembling the per-chunk outputs back into one result per sample. Prevents DeepCoil2 in particular from ever being forced to process an entire proteome as a single task.
- `--gpu_concurrency`: how many GPU tasks may share one GPU at once on the `local` executor (default: derived from the GPU's VRAM, which is 1 — strict serialization — on cards up to 40GB or when VRAM can't be determined; `0` disables the lock and throttle). See `docs/usage.md`, "Resource sizing and GPU sharing".
- `bin/detect_host_resources.sh`: reports a host's CPUs, RAM (cgroup-aware), GPU count and VRAM. Used lazily per task (`task.ext.host` in `conf/base.config`, memoized for the run) to size chunk-task requests, never above what the host can provide, and only on the `local` executor. Explicit `process.resourceLimits` still take precedence.
- `bin/gpu_lock.sh`: a real host-level `flock` semaphore for GPU tasks (see `Fixed`). Each GPU task's `.gpu_lock.log` records the slot it took and its wait.
- New labels `process_medium_chunk` (DeepCoil2, DeepLoc2, SignalP6, DeepTMHMM) and `process_high_chunk` (InterProScan), sized for one chunk rather than a whole proteome.
- **Phobius now runs once per chunk** too, with a new `PHOBIUS_MERGE` that writes the rows back in the cleaned FASTA's record order (FASTA_QC's `seqkit split2` distributes records round-robin, so plain concatenation would reorder them). Phobius is single-threaded: on the full R570 proteome it took 8.8h as one task vs ~7min across 1000 chunks, and the merged file is byte-identical (same md5) to the unchunked one.
- **VRAM-weighted GPU sharing** (the new default for an unset `--gpu_concurrency`): each GPU's usable VRAM is split into 512MiB units and a task holds as many as its tool's measured peak needs (`ext.gpu_vram_mb`: SignalP6 2200, DeepLoc2 3600, DeepTMHMM computed per chunk from its longest protein, see below; DeepCoil2 `all`, since its VRAM grows with chunk size), with a per-tool `maxForks` to match (`bin/gpu_max_forks.sh`). Previously every tool was assumed to need DeepCoil2's 19.2GB worst case, which fully serialized all four GPU tools on cards up to 40GB — on the full R570 run, 121.7h of GPU work back to back while the GPU averaged 21–44% utilisation. Sharing leaves every tool's output unchanged (same real chunk alone vs. sharing the GPU: identical results for all four tools); on a real 2400-protein R570 subset (8 chunks) the GPU stage took 35.7min instead of 55.6min (1.56×), and the whole run 36min instead of 56min, with byte-identical final RGA predictions. An explicit `--gpu_concurrency N` keeps its old meaning (N tasks of any tool per GPU).
- **Two-level merge** for samples with more than 1000 chunks: every `*_MERGE` fan-in goes through `splitForMerge` (`workflows/rgaprofiler.nf`), which first merges batches of ≤1000 chunks (`*_MERGE_BATCH`, same module, unpublished) and then merges those. Needed because Nextflow writes one staging line pair per input into a single bash function in `.command.run`, and bash segfaults (exit 139) parsing it somewhere past ~10k inputs, before the task's script ever runs. Verified at 60,000 chunks per tool.
- **Per-chunk, per-tool resource models.** Each chunk task's memory, time and (for DeepTMHMM) GPU memory are now computed from what is actually in its chunk (`task.ext.chunk`: sequences, residues, longest protein, read from the chunk FASTA and memoized) and from the tool, instead of one rule shared by all four GPU-capable tools. What drives each was measured: peak RSS of every task of a real 1000-chunk R570 run joined to its chunk's composition, and single proteins of 1k–35k residues through the whole pipeline on GPU and CPU. Host memory is model-bound and nearly flat in protein length (SignalP6 ~3.5GB, DeepTMHMM ~5.5GB, DeepLoc2 ~10.3GB); only DeepCoil2 and InterProScan grow with chunk size. SignalP6 now reserves 5GB instead of ~15GB, DeepTMHMM 9GB, DeepLoc2 13GB, DeepCoil2 9GB (300-protein chunk), which leaves RAM for more InterProScan chunks while GPU tools share the card. Time limits scale with the chunk's residues and CPU vs GPU (never below the previous fixed 8h/16h), so large chunks on CPU are no longer killed at a fixed wall.
- **DeepTMHMM's GPU-lock need follows each chunk's longest protein** (measured 3.7GB at 2,500 residues, 5.6GB at 10,000, 11.7GB at 35,000): with the fixed 4.6GB weight, a proteome with titin-sized proteins could have packed three such tasks onto one 20GB card.
- **`--num_blocks auto`**: `FASTA_QC` picks each sample's chunk count from its cleaned sequence count and the CPUs of the machine running the pipeline (chunks of 100–500 sequences, about two rounds of InterProScan tasks across the CPUs), logging the chosen count so it can be passed back explicitly. Opt-in, because chunk composition slightly affects some tools' numbers (below). A startup warning suggests it when the default chunking leaves most of the machine's CPUs idle.
- **`--deeptmhmm_cpu_threads N`** (CPU runs only, opt-in): cap DeepTMHMM's torch threads. By default `predict.py` uses one thread per host core, which on a 256-core host took ~3.75h per 300-protein chunk vs 836s at 6 threads; the thread count changes its saved embeddings at the floating-point level (predictions identical in testing), so it is not the default.
- Documented that **chunk composition slightly affects some tools' outputs**, measured by predicting the same 100 proteins in two differently-composed chunks: none for Phobius, DeepLoc2 and DeepTMHMM; SignalP6 probabilities ≤0.000007; DeepCoil2 per-residue scores ≤0.003 on GPU (≤0.19 on CPU, never across 0.5); InterProScan Gene3D boundaries for 1 of 100 proteins. The pipeline therefore never changes the chunking on its own.
- **`run_metadata.json` records the chunking and CPU/GPU mode** (`rga/<sample>/run_metadata.json`, block `pipeline_settings`): `num_blocks`, `fasta_qc_chunk_size` and `use_gpu` as requested, plus what they resolved to for that sample — `n_chunks` (e.g. the count `--num_blocks auto` chose) and `gpu_used`. Both slightly affect some tools' numbers (full R570 vs the `rgapredictor` reference: ~6k of 375k InterProScan Gene3D hits differ, Pfam identical; DeepCoil2 scores up to ~0.02), so `docs/usage.md` now advises keeping `--num_blocks` and `--use_gpu` fixed across runs being compared. `pipeline_info/params_*.json` only showed the requested values (`auto`).
- Tests: `tests/bin/test_fasta_qc.sh` (terminal vs internal stop codons, output sequences and `WARNING` lines).
- Tests: `tests/bin/test_host_resources.sh`, `test_gpu_lock.sh` and `test_resource_sizing.sh` (mocked 256-CPU/503GB, 2-CPU/8GB and GPU-less hosts; lock mutual exclusion, slot count, kill-release and fail-open) and `tests/resources.nf.test` (chunk labels under `-profile test`'s CI-sized `resourceLimits`).

### `Changed`

- **Output layout (breaking): every result is now published as `<outdir>/<tool>/<sample>/`**, e.g. `rga/<sample>/rga_predictions.tsv`, `deepcoil2/<sample>/<protein>.out`, `summary_report/<sample>/report.html` (previously `rga/rga_out/…`, `deepcoil2/results/…`, `summary_report/report_out/…`, `fasta/<sample>_clean.fasta`). With several samples in one run, same-named files used to overwrite each other in the shared per-tool folders — every sample's `rga_predictions.tsv`, SignalP6's `region_output.gff3`/`processed_entries.fasta`, DeepTMHMM's summaries — so only the last sample's survived. The modules' internal `results/`, `rga_out/` and `report_out/` levels are no longer repeated in the published paths. Contents are unchanged (the pipeline test snapshot's checksums are identical; only paths moved). Update any scripts that read the old paths.

### `Fixed`

- **`FASTA_QC` silently deleted internal stop codons.** Every `*` was removed, so an internal one (pseudogene or broken gene model) joined the residues on either side into a protein that doesn't exist (`MK*LV` → `MKLV`), with nothing logged. Now only the trailing stop is stripped; an internal `*` becomes `X` (`MKXLV`) and is logged as `WARNING: N internal stop codon(s) (*) in sequence <id> replaced with X`. Inputs without internal stops give the same cleaned FASTA as before. Stripping the trailing `*` is intentional but changes results compared with runs on a FASTA that still has it (DeepTMHMM/DeepLoc2 score it as ESM-1b `<unk>`, SignalP6/DeepCoil2 as `X`), including the current `rgapredictor` R570 reference: about 1.5% of the R570 RGA calls differ, mostly TM-CC. Documented in `README.md` and `docs/output.md`.
- The summary report's links to each tool's results were broken (they pointed to `summary_report/rga/…`); they now point to the same sample's folders in the new layout.

- CLI-provided integer/boolean parameters (e.g. `--num_blocks 1000`) failing pipeline parameter validation (`Value is [string] but should be [integer]`) under Nextflow 26.04's v2 syntax parser, which always parses CLI flags as strings. `validation.lenientMode` (a prior attempt at this fix) does not perform this cast and was a red herring; the actual fix is nf-schema's `cast_cli_params` option, which requires `nf-schema>=2.7.2` (bumped from `2.5.1`) and is now enabled via `cli_typecast: true` in `utils_nfcore_rgaprofiler_pipeline`'s call to `UTILS_NFSCHEMA_PLUGIN`. See [nf-core/blog: Why parameters are strings all of a sudden](https://nf-co.re/blog/2026/parameter-types). A params file (`-params-file`, see `assets/params.example.yml`) remains the more robust option for typed parameters regardless, since the cast only affects validation, not the runtime `params` values themselves.
- **Chunked tools starving each other at high `--num_blocks`** (observed on a full-scale proteome with `-profile docker,long_running --num_blocks 1000` on a 256-CPU/503GB/20GB-GPU host: InterProScan kept progressing while DeepCoil2, DeepLoc2, SignalP6 and DeepTMHMM stalled). Two compounding causes:
  - **Memory sized for the wrong execution model.** `long_running`'s `process_medium` (150GB) was calibrated for these four tools running once against a whole proteome, but they run once per chunk. Measured peak RSS per chunk task on that run was 3.8–10.5GB (InterProScan 8.8GB, which was likewise reserved at 100GB), so only ~3 `process_medium` tasks and ~5 InterProScan tasks ever fit in RAM, competing for the same 503GB. The five chunked tools now carry their own labels whose memory is a floor plus a term proportional to the chunk's FASTA size (times `task.attempt`), capped at 90% of the host on the `local` executor (roughly 14–15GB per GPU-tool chunk and 11–12GB per InterProScan chunk at ~300 sequences, versus 150GB/100GB before); `long_running` only raises their time ceiling. `process_medium` under `long_running` (now used only by `RGA_CLASSIFY`, measured ~2.8GB) drops from 150GB to 16GB.
  - **GPU exclusivity faked through CPU admission control.** `process_gpu` reserved 75% of the host's CPUs per task so Nextflow would run one at a time; InterProScan's continuous stream of small CPU tasks kept refilling freed capacity, so such a task could starve indefinitely while the GPU sat idle, and it ignored VRAM entirely. Replaced by a real host-level lock (`bin/gpu_lock.sh`, sourced from `beforeScript`, held for the whole task, released by the kernel if the task dies) plus a per-process `maxForks` cap so `--num_blocks 1000` doesn't park hundreds of idle tasks on the lock. `process_gpu` no longer inflates `cpus`.
- Measured GPU footprint, for reference (RTX A4500, one chunk per task, ~300 / ~4900 sequences): peak VRAM DeepCoil2 10.9 / 19.2GB (grows with chunk size — keep chunks around the default 5000 sequences or fewer on a 20GB card), DeepTMHMM 3.7 / 4.0GB, DeepLoc2 3.1 / 3.1GB, SignalP6 1.9 / 1.9GB; peak RSS DeepCoil2 6.4 / 16GB, DeepLoc2 10.3 / 10.3GB, DeepTMHMM 5.4 / 5.5GB, SignalP6 3.5 / 4.3GB, InterProScan 6.5GB / 7.6GB (at ~300 / ~1000 sequences).
- InterProScan chunk tasks now request 6 CPUs instead of 12. `-cpu` is only an upper bound on its threads: measured use on a real 1000-chunk run was median 3.3 cores (max 4.0), and one chunk ran in 16m24s at `-cpu 6` vs 16m45s at `-cpu 12`. Twice as many chunks can now be admitted at once.

- **`Argument list too long` (exit 126) in `DEEPCOIL2_MERGE`** on a full-scale proteome (1000 chunks, ~300k `.out` files), and the same latent failure in the `cat`/`cp` calls of `INTERPROSCAN_MERGE`, `SIGNALP6_MERGE` and `DEEPTMHMM_MERGE` at higher chunk counts: file lists now go from a bash array through the builtin `printf` to `xargs`, which batches them under `ARG_MAX`. This also replaces `DEEPTMHMM_MERGE`'s one-`cp`-per-embedding loop, which took 201 minutes on the full R570 run; since identical sequences in different chunks produce the same content-hash embedding name (and one `cp` call refuses to write a name twice), only the last occurrence of each name is copied, which is what that loop left in place. `SIGNALP6_MERGE` and `DEEPTMHMM_MERGE` now also accept their own merged output as input (for the two-level merge above).
- `use_gpu`/`gpu_concurrency` comparisons in `conf/base.config` and `workflows/rgaprofiler.nf` now go through `toString()`: an unquoted `use_gpu: false` in a `-params-file` arrived as a Boolean and still capped every GPU tool at one task at a time on a CPU-only run (`maxForks = 1`), and an unquoted `use_gpu: true` silently ran on CPU. `--gpu_concurrency 0` from the CLI (a String under the v2 parser) likewise didn't disable the lock.
- `--use_gpu false` / `--use_gpu true` were rejected by parameter validation (`Expected any of [[auto, true, false]]`) — from the CLI and even as a quoted string in a `-params-file` — because the value reaches nf-schema as a Boolean. The schema now accepts `"auto"`, `"true"`/`"false"` and `true`/`false` (anything else is still rejected); the config already treats both forms alike (see below).
- A warning at startup when `--use_gpu true` / `-profile gpu` is set but no usable NVIDIA GPU is visible, instead of every GPU task failing inside the container runtime.
- On the `local` executor each CPU-mode DeepTMHMM task now reserves the whole machine: its threads always equal the host's core count, so concurrent tasks oversubscribed it (4 at once on a simulated 24-core host: ~2.2h per chunk each vs 383s alone; the host's load average reached ~750 on a 256-core machine). Output unchanged. SignalP6 on CPU now reserves the 8 CPUs its 8 torch threads use (was 6).
- DeepLoc2 on CPU (`--use_gpu false`, or `auto` without a GPU) now runs with `OMP_NUM_THREADS` set to the task's CPUs instead of one torch thread per host core in every concurrent task. Output unchanged (byte-identical CSV at 6 vs 64 threads on a real chunk); the GPU path is untouched.
- InterProScan chunk tasks now request 4 CPUs (was 6) and a 10GB memory floor (was 11GB). On the full R570 run they used median 3.1 cores and at most 7.8GB (8.8GB in an earlier run), and the 11.5GB reservation, not CPUs, capped them at 39 concurrent tasks on a 503GB host (now 43). A real chunk gave the same result rows at `-cpu 4` and `-cpu 6`, no slower; InterProScan's row order varies between runs even at the same `-cpu`.

- **`rga_classify` crashed on samples with no domain evidence at all** (`ValueError: No objects to concatenate` in `evidence._build_long`), e.g. a small protein set with no InterProScan hits of the collected kinds — failing the run instead of reporting zero RGAs. Patched in the vendored source (`docker/rga_classify/src/code/rgas/rga/evidence.py`; to be upstreamed to omatheuspimenta/rgapredictor): an empty evidence table is returned instead. Re-running 9 real `RGA_CLASSIFY` tasks with the published 0.0.1 image and the patched build gave identical outputs (only the report's generation timestamp differs), and the crashing task now completes with 0 RGAs. Published as `ghcr.io/omatheuspimenta/rga_classify:0.0.2`, which `RGA_CLASSIFY` and `RGA_REPORT` now use (was 0.0.1).

- **`deepcoil2` image no longer built** (`apt-get` exit code 100): its base, `python:3.7-slim-bullseye`, is Debian 11, now past end-of-life, and the bullseye-security index on `deb.debian.org` listed updated packages whose files already returned 404. Both build stages now install from `archive.debian.org` (`main` + `bullseye-updates`). A rebuild with this fix has exactly the same system packages as the published `deepcoil2:2.0.2` (OpenBLAS included) and the same Python packages except `pytz`. Python 3.7 images exist only for Debian 11 and older, so moving the base forward isn't an option for DeepCoil's pinned 2020-era stack.
- **The image-publishing workflow no longer replaces published tags.** It used to rebuild all seven images on every release and push them over their existing tags, so a routine run silently replaced five published images (`phobius`, `interproscan`, `deeploc2`, `signalp6`, `deeptmhmm`) with rebuilds carrying newer OS/Python packages. It now skips any image whose tag is already published; a manual run with `overwrite` ticked is the only way to replace one. A changed image should get a new tag.
